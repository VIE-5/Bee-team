## 事故处置：LibreOffice 误报「bootstrap.ini 已损坏」

**起因**：主人截图报障——手动双击 LibreOffice 弹「配置文件 bootstrap.ini 已经损坏」。
**归属**：我上一轮跑 LibreOffice 批量转 PDF 留下的僵尸进程所致（但配置文件本身完好）。

### 处置过程
1. 查 `bootstrap.ini`：112 字节、内容完全标准 → **报错是误报**。
2. 查进程：`soffice.exe`(18480) + `soffice.bin`(26188) **仍僵死运行**（已跑 3.5 小时）。
3. 查命令行 → **抓到铁证**：两个进程的参数里路径全是 `/d/WORK——Vie/...` 形式，
   即 **Git Bash 没有把 Unix 路径转成 Windows 路径**（因为路径含 `——` 与中文）。
4. 同时发现：`00-原始PDF/` **一个文件都没有** → 那次批量转换**根本没成功**（静默零产出）。
5. 用 PowerShell `Stop-Process -Force` 杀掉两进程（`taskkill //F` 在 Git Bash 里传参会失败）。
6. **实测验证**：用「Windows 风格路径 + 纯 ASCII 临时配置目录」转一个小文件 →
   PDF 正常产出 13915 字节、退出码 0、无残留进程、报错不再出现 → **LibreOffice 健康**。

### 根因（两条独立）
1. **路径转换失败**：MSYS 只对纯 ASCII 路径做转换 → LibreOffice 收到非法路径 → 零产出且不退。
2. **单实例锁冲突**：僵死进程占着配置目录锁 → 用户新实例抢不到锁 → LibreOffice 把它**误报成文件损坏**。

### 结论与教训
- **「退出码 0」≠「任务成功」**：那次转换退出码是 0，产物是 0 个。以后跑产出型命令必须**核对产物**。
- **教训根源**：我当时没核对 `00-原始PDF` 就往下走了。所幸后来改走 `ppt/media` 直接提取原图
  （效果比转 PDF 更好），任务没受影响 —— **但这是运气，不是流程**。
- 已删除误导性的空目录 `00-原始PDF/`；归档文档未失实记录（已核 grep）。
