八大发现

从引用网络里读出的结构特征——前四条是健康设计，后四条是待处理的结构缺口。

01双枢纽：踩坑库 + 能力注册表

踩坑库出度 13、入度 13（总度数 26，全体系第一）——既是知识输出源，又是被引用最多的一环。能力注册表（13/7）紧随其后。知识层是这张网的重心。

02纯契约：派工单模板（出 0 / 入 12）

它零出度——不依赖任何其他文档，却被 12 处引用。这是教科书式的"契约"设计：协议层本身不含依赖，脆性最低。验收清单（2/10）同理。

03最重的执行者：图片施工蜂（8/9）

依赖最多工具与规范（render-deck / deck2pptx / PPTX规范 / 矢量Logo链 / 母版），同时被引用最多。它是执行层的主承重墙——它一停，全案出图链路即断。

04质量闸门:守卫蜂的"轻依赖、重被引"（3/9）

只依赖 render-deck + 验收清单 + 派工单，却被 9 处引用。质量检查者只锚定少量稳定接口，不绑定生产细节——分工干净。

05单向俯瞰：制度总纲（出 16 / 入 2）

制度总纲俯瞰所有人，却几乎不被回头引用（仅全景图 V2 与踩坑库）。规则层→执行层是单向边：改了制度，工蜂卡不会收到失效提醒。

06反向引用缺口：工蜂卡不锚规则

五张工蜂卡普遍只引用「派工单」，均未回链「制度总纲 / 能力注册表」。执行者的"我该守什么"只写在知识层一侧，工蜂卡自身不声明所循规则。

07孤岛：社媒KV手册 / 两个工具 README

社媒KV确定性合成手册入度仅 1（只被制度总纲提及一次）；deck-benchmark、矢量Logo链的 README 各仅被踩坑库引用 1 次。它们有内容，却几乎没接进运转链。

08展示层脱节：全景图 / 架构理解的入度均为 1

V1、V2、架构理解 V1 入度全部只有 1（且仅来自 README 索引）。它们是"给人看的"，与工蜂的运转链零耦合——必然不会自动跟随体系演进（本次 main→master 修正即为实例）。
