# 踩坑库

> 每次验收打回（C 级）或任务踩雷，都要往这里写一条。**踩过的坑不许踩第二次。**

## 格式

```markdown
### {YYYY-MM-DD} · {一句话坑描述}

- **场景**：当时在做什么任务
- **现象**：出了什么幺蛾子
- **根因**：为什么会发生
- **解法**：怎么绕过去 / 修好的
- **防复发**：写进哪个角色卡的哪条 / 哪份清单要加什么
```

### 2026-09-27 · 交付 PDF 全册 100% Type3（一个字体都没嵌入）——可变字体是根因

**现象**：碗香交付 PDF 用 PyMuPDF 读字体表，**没有任何一个非 Type3 字体**。对照标杆（土蚝 V6，60 页）却有 `Georgia / Georgia-Bold / Arial-BoldMT / ArialMT` 真实嵌入（Type3 占 95%，即全部中文）。

**根因隔离实验**（`_work/font-probe/ft2.py`，同一段「Latin ABC 1234 ｜ 碗香中文」换字体族渲染）：

| 字体族 | PDF 内实际字体 | 本机字体文件 | 结论 |
|---|---|---|---|
| Noto Serif SC | **Type3** | `NotoSerifSC-VF.ttf` | **可变字体** |
| Noto Sans SC | **Type3** | `NotoSansSC-VF.ttf` | **可变字体** |
| STZhongsong / PingFang SC / MS Song | Type3 | 未安装 | 走系统回退 |
| SimSun · Microsoft YaHei · SimHei · KaiTi · FangSong | 真实嵌入 ✔ | 静态 ttc/ttf | — |
| Georgia · Arial · Times New Roman | 真实嵌入 ✔（仅拉丁） | 静态 ttf | — |

**判据（可直接复用）**：

> **Chrome headless 打印 PDF 时 —— 字体族最终命中「可变字体（VF）」或「未安装字体（走系统回退）」→ 只能退化为 Type3 字形程序；命中「已安装的静态字体」→ 真实嵌入。**

碗香的 `--font-serif: "Noto Serif SC",…` 与 `--font-sans: "Noto Sans SC",…` **首项都是 VF** → 全册 100% Type3。
土蚝 V6 排中文同样用 VF（故 95% Type3），但西文层用的是静态 Georgia/Arial → 那 5% 是真嵌入。

**影响面**：Type3 字形轮廓精确、无字体依赖、无授权问题，多数现代 RIP 可正常输出；风险在**部分印厂 preflight 会因「未嵌入字体」报警**。**必须区分「视觉缺陷」与「交付工艺项」—— 它不是看起来不对，是工艺上不稳。**

**处置选项**：

| 选项 | 做法 | 视觉 delta | 代价 |
|---|---|---|---|
| **A**（推荐） | `@font-face` 指向**静态** Noto Serif SC / Noto Sans SC（OFL，可商用可嵌入） | ≈ 0（同字族） | 需下载静态字重（400/500/600/700 × 2 族）；PDF 略增 |
| B | 字体栈改已装静态字（SimSun / 微软雅黑 / 黑体） | **1.479%（SimSun）/ 1.615%（雅黑）像素差 = 换字** | 触及 BrandLock 字体规范，须主人确认 |
| C | 保持现状（Type3） | 0 | 印厂 preflight 可能报警 |

**排查动作（值得固化为验收项）**：交付前读 PDF 字体表，**统计非 Type3 字体数**；若为 0 或明显偏少，按上表定位。此前的验收只查了页数 / MediaBox / 文本层，**完全没有覆盖「字体嵌入」这一维**。

### 2026-09-22 · 「一物料一页」单张展示页型的几何配方

适用：物料/器物/服装等**多张等比例素材独立入册**的展示段落。
配套：`.mat-single` 页型（`01-工蜂产出/assets/theme.css`），生成脚本 `_中间文件/build-materials-single.py`。

固定画布 1360×850，全部**硬编码 px**（R7 —— 绝对定位下百分比与 auto 尺寸解析不可靠）：

```
内容区 = 左右 --mx(149.6) · top --hdr(127.5) · bottom 10%(85)  → 1060.8 × 637.5
  mat-head（页题 + 英文行）        62 + margin-bottom 16 = 78  → 余 559.5

```

三条硬约束的检查方式：
- **零页眉页脚冲突** → 图框锁在内容区内 + 几何余量 > 0，无需目视逐页猜
- **零遮罩/渐变** → `.ph` 只用 1px 实线边框 + 纯色底；收尾正则检索 `gradient` 数 == 0
- **一图一页** → 收尾核对 `class="mat-single"` 出现次数 == 素材张数，且 `class="mat-pair"` 残留 == 0

### 2026-09-15 · Git Bash 不转换含中文/破折号的路径 → 外部程序静默失败 + 进程僵死

- **场景**：VI 案例母版拆解任务，用 LibreOffice headless 批量把 5 个 PPTX 转 PDF
- **现象（两个，相隔几小时才串起来）**：
  1. 后台转换任务「跑完了」但 `00-原始PDF/` **一个文件都没有**——静默零产出
  2. 数小时后主人手动双击 LibreOffice 图标，弹出**「配置文件 bootstrap.ini 已经损坏」**
- **根因**：
  1. **Git Bash(MSYS) 只对纯 ASCII 路径做 Unix→Windows 转换**。蜂巢路径含 `——`（em dash）与中文，
     MSYS 放弃转换 → LibreOffice 实际收到 `-env:UserInstallation=file:////d/WORK——Vie/...`、
     `--outdir /d/WORK——Vie/...`、源文件 `/d/360MoveData/...` 这类**非法路径** → 找不到文件、
     连输出目录都不合法 → **退出码仍是 0，但零产物**
  2. LibreOffice 是**单实例**程序：这次启动的 headless 实例一直僵死不退，占着配置目录锁。
     主人再手动启动时新实例抢不到锁，LibreOffice 把「锁冲突」**误报成「bootstrap.ini 已损坏」**——
     **配置文件其实是好的**（112 字节、内容完全标准，见下）
- **误报实测证据**：`C:\Program Files\LibreOffice\program\bootstrap.ini` 内容
  ```
  [Bootstrap]
  InstallMode=<installmode>
  ProductKey=LibreOffice 26.2
  UserInstallation=$SYSUSERCONFIG/LibreOffice/4
  ```
  → 完好。**别信这个报错，先查进程。**

- **解法**：
  1. 杀僵死进程：`Stop-Process -Id <soffice.exe/soffice.bin> -Force`（`taskkill //F` 在 Git Bash 里 `//F` 会被原样传入而失败，改用 PowerShell）
  2. **给外部 Windows 程序传路径必须用 Windows 风格**（`C:/...`），不要指望 Git Bash 转换中文路径
  3. `-env:UserInstallation` 一律指向**纯 ASCII 临时目录**，如 `file:///C:/Users/<u>/AppData/Local/Temp/xxx/prof`
  4. 修好后**实测验证**：转一个小文件，PDF 正常产出 + 无残留进程 = 健康

     ```
     deck  rect.h = 1080        ← 父元素正常
     slide rect.h = 144         ← 子元素塌了
     slide top=0 bottom=0       ← 计算值全对，但没生效
     ```
  5. ✅ **逐条试改**，找到两个能让它恢复 1080 的操作：
     ```
     >> force height:1080px   -> 1080.0   ✅
     >> deck transform:none   -> 1080.0   ✅   ← 这句直接指向 transform 是元凶
     ```

- **解法**：

  ```css
  /* 满幅层一律写死高度，不要只靠 inset:0 / bottom:0 */
  .slide   { height:100%; }
  .dv-wrap { position:absolute; inset:0; height:100%; }
  .bleed   { position:absolute; top:-72px; left:-96px; right:-96px; bottom:-72px;
  ```

### 2026-09-18 · Windows headless 渲染链路的五个隐蔽陷阱（碗香 LOGO 封装单）

**共同特征：全部以「产物存在但内容是错的」形式出现 —— 退出码 0、文件也确实生成了，
你只会以为是自己改动没写对。这比"零产出"更阴险。**

#### 坑 1 · `<figure>` 的 UA 默认 margin 让网格静默掉列

- **现象**：11 张 Logo 的四列网格实际渲染成 3 列 → 3 行变 4 行 → 首行被页眉切、末行溢出画布被裁

- **根因**：`<figure>` 带浏览器默认样式 `margin: 1em 40px`，每格凭空多占 **80px**

- **解法**：渲染 URL 追加时间戳 `?v=<ms>`（已内置为 render-deck.py 的 `cache_bust()`）
- **防复发**：凡「改了前端资源重渲染没变化」，**先怀疑缓存，别怀疑自己的编辑**

#### 坑 3 · Windows 控制台 GBK 编码三连

- **现象 A**：脚本 3 页渲染全成功，却崩在收尾那句 `print("  ✓ 全部通过体积体检")`
  → `UnicodeEncodeError: 'gbk' codec can't encode '\u2713'`，
  **且这个异常把后面的 PDF 导出整个挤掉了**
- **现象 B**：为绕开 A 把 `sys.stdout.reconfigure(encoding="utf-8")`，PowerShell 又按 GBK 解码这些

- **现象 C**：诊断时 `> out.txt 2> err.txt` 分流，读到的 err.txt 被判为二进制

- **正解**：**保留系统编码输出**（GBK 本来就支持中文），只把输出符号全改 ASCII

#### 坑 4 · `subprocess.DEVNULL` 在 Windows 上不是黑洞

- **收尾**：仍残留的异步 traceback 用 `threading.excepthook` **精准静默**

#### 坑 2 · 内联 JS 的 `'\n'` 被 Python 三引号串提前转义

- **现象**：DOM 探针脚本"跑通了"，`--dump-dom` 也确实抓到了 `ZZSTART...ZZEND` 之间的内容，
  但内容是 `' + L.join('\n') + '` —— **那是脚本源码的片段，不是测量结果**
- **根因**：Python 普通三引号串里 `\\n` 会先被 Python 转成 `\n`（字面反斜杠 n），

- **解法**：探针脚本改用 **raw string** `r'''...'''`；关键标记再用 `String.fromCharCode(10)` 兜底；
  匹配时取 `re.findall(...)` 的**最后一个**（源码在前、执行结果在后）
- **防复发**：**凡生成内联 JS 的脚本，一律 raw string**；
  "有输出" ≠ "输出对" —— 要确认内容是**执行结果**而非源码回显

#### 坑 3 · 带 `transform:scale()` 祖先时，DOM 量出的尺寸偏大

- **现象**：DOM 实测 11 张图片尺寸为 724.0 / 482.7 / 1000.3，
  而 CSS 设计值与像素法反推值都是 718 / 478.6 / 992 —— 差约 0.8%
- **根因**：`.deck` 带 `transform: scale(var(--z))` 做视口适配，
  `getBoundingClientRect()` 返回的是**视觉尺寸**（已乘 z），
  还原时「除以 z」这一步引入两次量化误差（Chrome 对 transform 后的 rect 有 subpixel 舍入）
- **解法**：**测量前先摘掉缩放** ——
  ```js
  deck.style.transform = 'none';        // 改完直接读，getBoundingClientRect 会强制 reflow
  var w = img.getBoundingClientRect().width;   // 此时即 1:1 布局真值，无需再换算
  ```
  实测立得 **718.0 × 718.0**，与设计值分毫不差
- **防复发**：**DOM 测量要量"布局值"，就先把影响布局的 transform 摘掉**；
  缩放还原只作兜底，不作判据

#### 坑 4 · 同一轮里目测三次全错

| 我目测的结论 | 实测结果 |
|---|---|
| 「图片溢出图台被裁」 | 像素法 + DOM 法均证明图片 718×718 完全在图台内 |
| 「说明文字只占容器一半宽」 | 实测文字 x[1251,1829] 宽 **579**，设计值 584 |
| 「图片显示得太小」 | 原图元素占比反推 **717.0**，设计值 718 |

- **根因**：Read 读图返回的是**缩放后的预览**（1920px 图被压到约 1094px 显示），
  在缩放图上目测像素边界，误差被系统性放大
- **解法（三条都可交叉验证）**：
  1. **像素法** —— PIL 扫包围盒。**必须限定扫描区**：本轮首扫把页眉的朱红编号
     和右侧说明小标题一起算进了包围盒，得出荒谬的 1280px
  2. **DOM 法** —— 注入脚本读 `getBoundingClientRect`（先移除祖先 transform，见坑 3）
  3. **反推法** —— 原图里某元素的占比已知 → 从截图反推图片渲染尺寸
- **防复发**：**R9 加强版 —— 「看起来不对」也必须先量再改，而且量之前要确认"看"的这张图有没有被缩放。**
  拼接核查图若被压得过小，改裁切局部看原尺寸，别在压扁的图上做判断。

### 2026-09-18 · 反白稿做成「纯白剪影」：深色载体上标志全废（母版级缺陷）

- **场景**：碗香 Logo「二」5 页方案展示册。P5 综合应用页要把标志上到**深色载体**
  （门头灯箱深色底板 / 深底员工围裙 / 名片红卡），用的是 `-reverse.png` 反白稿。
- **现象**：这三处的标志呈**一坨没有任何结构的白色轮廓** —— 内部文字「碗香」、人物五官、
  发际线、轮廓描边全部消失，只剩一个白色圆头剪影。整体观感像"图挂了/做坏了"。
  同一页另外两个载体（碗盖彩稿、木牌墨稿）却完全正常。
- **根因**：反白实现沿用首单写法 ——

  ```python
  white = Image.new('L', im.size, 255)
  rev = Image.merge('RGBA', (white, white, white, im.getchannel('A')))   # ← 错
  ```

  它保留了 alpha 轮廓，但把 RGB **全部拉平成 255**，
  **"字与底""人与底"的明暗关系被抹平** —— 而标志的识别性恰恰全靠这层关系。
  深底上剩下的当然只是一个白块。

- **解法（已验证）**：改「**双色互换**」—— 按亮度二值化，暗部映射为白、亮部映射为本版主色：

  ```python
  lum = gray.point(lambda v: 255 if v >= 128 else 0)             # 亮部掩膜
  rev = Image.composite(Image.new('RGB', size, PRIM[k]),         # 亮部 -> 本版主色
                        Image.new('RGB', size, (255, 255, 255)),   # 暗部 -> 白
                        lum)
  rev = rev.convert('RGBA'); rev.putalpha(im.getchannel('A'))    # alpha 原样保留
  ```

  效果：**白圆 + 主色字 + 主色人物剪影**，深底上结构完整、层级清晰、像一枚双色印章。

  **阈值 128 在三版上区分度极大**（实测 luma）：底色 暗红 52 / 墨绿 47 / 朱红 61（均 < 130），
  字与浅底 金 215 / 米黄 229 / 纸白 253（均 > 210）—— 中间是真空区，不会误切。

- **为什么首单没暴露**：首单 P5 也是同一写法、同样是白块，但当时逐页看的是
  **"整页骨架是否成立"**，没有放大看载体内部细节，于是漏过。
- **防复发**：
  1. `PPTX原生构建规范.md` §6 素材加工表的「反白稿」一行改为双色互换，并标注 ⛔ 禁止事项
  2. 固化为母版 `Logo-Scheme-Show-Master/prep-assets.py` 的标准做法（换素材自动继承）
  3. **判据**：反白稿生成后，**必须合成到深底上目视**；看不到内部结构 = 不合格，直接返工

### 2026-09-19 · 图片素材→册子封装：补边方式、老式数字、页眉页脚可读性（土蚝小院全案 25 页）

**场景**：主人给 18 张已成型的品牌全案版面（16:9 十张 / 4:3 七张 / 竖版一张，**尺寸混排**），
要求「封装成册、高级雅致、页眉页脚加上」。走的是 A 全案路线（自建主题 + `render-deck.py`）。

#### 坑 1 · 用「边缘条带拉伸」补边 → 照片页两侧拉出横条纹

- **做法**：原图 `contain` 居中后，四周用「原图边缘 16px 条带拉伸」补齐（左列纵拉伸、顶行横拉伸、四角取角块）
- **现象**：**纯色底的深墨绿页完全看不出问题**（拉伸纯色还是纯色），
  但一到照片页（主 KV / 应用页），两侧立刻出现一道道**横向条纹**，整页看着像"图挂了"
- **根因**：边缘条带本身含画面内容，把它单向拉伸等于**把一列像素拉成一片**，形成规则条纹；
  模糊半径（6px）远小于拉伸尺度，压不住
- **解法**：改 **「cover + 强高斯模糊」铺底** —— 原图 `cover` 到画布尺寸后高斯模糊（≈58px）做底层，
  前景 `contain` 居中叠上。色彩连续、无接缝，观感接近影院的柔焦延展
- **防复发**：**照片/渐变类页面补边一律禁用边缘拉伸**，统一走模糊铺底；
  纯色底页面两者等价，就直接统一成模糊铺底，少一条分支

#### 坑 2 · Georgia 是老式数字，页码 `03` 渲染成 `o3`

- **现象**：目录页码、页脚页码用 Georgia 排出来是 `o3` `o1` `o8` —— 数字"陷"在基线以下，很难读
- **根因**：**Georgia 默认输出 old-style figures（老式数字）**，`0/1/2` 等有升部降部差异，
  这是设计特性不是 bug
- **解法**：页码类元素加 `font-variant-numeric:lining-nums; font-feature-settings:"lnum" 1`
- **防复发**：**用 Georgia / Garamond / Baskerville 这类"有老式数字传统"的衬线体排数字前，
  先放大看一眼**；页码、编号、数据一律显式锁 `lnum`

#### 坑 3 · 页眉页脚压在照片上，同一套字色时明时暗

- **现象**：全册统一用暖米白做页眉页脚字 → 深墨绿页上很清晰，
  但白底的墨稿页、浅米底的应用页上**完全看不见**；反之若统一用深色字，深底页又废
- **根因**：18 张原图的底色**跨越"近黑"到"近白"两极**（实测页眉带亮度 20.5 → 255.0），
  单一套配色不可能覆盖
- **解法（已自动化）**：
  1. `prep.py` 生成每页后，**实测该页页眉带（y 0–76）与页脚带（y 1014–1080）的平均亮度**，写进 `meta.json`
  2. `build.py` 按亮度给页面挂 class：`hd-dark` / `ft-dark` / `light-band` / `mix-band`
  3. `theme.css` 据此切换字色（深底→暖米白 `#EDE6D6`、浅底→墨色 `#2D301B`）与遮罩方向（压暗 / 提亮）
- **要点**：**页眉与页脚分开判断** —— 实测有页面顶部偏暗、底部偏亮（应用页 ftr 亮度 202 vs hdr 70），
  一刀切会把一半做废

#### 附带定下的规矩：画幅要跟素材走

原图 1672×941（16:9）占多数，故画布定 **1920×1080**：内容区 1920×938，
原图缩放到 1667×938 —— **几乎 1:1，零缩放损失**。
若为"好看"选 16:10（如 1360×850），原图要缩到 0.79 倍，
**小字密集页（规范表、色卡 HEX 值）会直接糊掉**。→ **画幅选择的第一判据是"素材主画幅"，不是"版面偏好"。**

**沉淀**：流程固化为 `prep.py`（素材加工+亮度实测）→ `build.py`（数据表出 HTML）→ `render-deck.py`（渲染+PDF+联系表），
三脚本可复用于任何「成套版面 → 册子」任务。参考实现：`E:\唐V-work\土蚝小院\品牌全案封装\`。

### 2026-09-21 · 「左栏导言可读性」五连坑（土蚝小院·品牌视觉资产封装）

**场景**：24 张成品视觉资产（16:9 十张 / 4:3 十三张 / 竖版一张）封装成 40 页高级餐饮品牌全案册，
要求「视觉为主、文字为辅、页眉页脚展示细节」。版式核心是「右侧大图台 + 左侧一条导言」。

这一轮把「左栏文字压在素材上读不出」这个问题**连踩五层**，最后靠像素扫描逐层剥出来的。

#### 第 1 层 · 遮罩方向判据用错

- **做法**：沿用了上一册的 `bc(name)` —— 按**页眉带/页脚带**亮度返回 `light-band` / `mix-band` / `inv-band`，
  再把其中的 `light` 判定**转手**决定左栏遮罩是压暗（`side-dim`）还是提亮（`side-dim-light`）
- **现象**：`g01`~`g06` 六张「应用延展」页（招牌 / 名片 / 门帘 / 餐具 / 打包）导言几乎读不出，
  其余十几页却正常 —— 同一套代码，行为分裂
- **根因**：这六张素材是 **`mix-band`（上暗下浅）**：页眉带暗 → `light` 判定失败 → 挂压暗遮罩，
  但**左栏那一竖条其实是亮的**（实测 `side_luma` 135–181）→ 压暗遮罩 + `dark-text` 浅色字 = 对比度打架
- **解法**：`prep.py` 新增 `side_luma`（左栏区 x132–632 / y126–960 平均亮度），
  `build.py` 新增 `side_cls()` **独立判定左栏**，不再转手借用页眉页脚结论
- **实测对照**（修正前后）：

  | 页 | 左栏 avg（前） | 左栏 avg（后） | 遮罩 → 结果 |
  |---|---|---|---|
  | P24/25/27/28 | 29–39 | 29–39 | `side-dim` 压暗 + 浅字 ✅ |
  | P32 | 67.8 | **196.0** | `side-dim-light` 提亮 + 墨字 ✅ |
  | P33 | 87.2 | **201.5** | 同上 ✅ |

- **防复发**：**任何"遮罩/字色方向"类判据，都必须是"离它最近的那块区域"的实测值**，
  不能用十几厘米之外的另一块区域的结论代替

#### 第 2 层 · 文字色硬编码，`dark-text` 翻不过来

- **现象**：按第 1 层改完后，P32/P33 的**背景**确实提亮了（实测 67→196），但导言**还是读不出**
- **根因**：`.plate-sub` / `.plate-cap` **硬编码**了 `color:var(--light-2)` / `var(--light-3)`（浅色），
  `.plate-lead` 干脆**没写 color**、只靠继承 —— 整套「`dark-text` 翻成墨色」的机制对这三行完全失效
- **解法**：补 `.slide.dark-text .plate-lead/.plate-sub/.plate-cap/.plate-idx/.plate-rule` 五条覆盖
- **要点**：**"主题色切换"类机制只有在元素"用变量且被主题变量覆盖"时才生效**；
  硬编码了一个色值，就等于把自己排除在主题之外 —— 改完必须**逐元素核对**，不能只看大面积观感

#### 第 3 层 · 图台没让开左栏

- **现象**：`b01`/`c01` 等页的导言右半被素材**整齐地**切掉
- **根因**：`.plate-stage` 定为 `width:1284px`（x 636–1920），而 mate 出来的前景图宽 1227px、
  左边界在 `(1920−1227)/2 = 346px` → **直接重叠 300px**
- **解法**：`.plate-stage` 收窄为 `width:1190px`（x 730–1920），让左栏 x132–652 之外留 78px 安全缝
- **防复发**：**设计"图 + 文"分栏时，不能只规定"文字占多宽"，还要反推"素材 contain 后实际落在哪"** ——
  图台宽度必须按 `(画布宽 − 前景宽)/2` 反算，而不是拍一个好看的数

#### 第 4 层 · 满幅图版成了漏网之鱼

### 2026-09-21 · 多张固定尺寸 deck 的截图三连坑（土蚝小院·品牌视觉资产封装）

**场景**：24 张成品视觉资产封装成 **37 页**品牌全案册。画幅沿用母版 **1360×850（16:10）**，
结构是母版规定的「**多张固定尺寸 `.slide` 纵向平铺**」（一个 HTML 里平铺 37 个 1360×850 的 div），
用现成工具 `04-知识沉淀/工具/render-deck.py` 出 PNG + PDF。

这一轮是**「产物存在但内容是错的」**的典型 —— 三处失败全部不报错、退出码 0、文件也确实生成了。

#### 坑 1 · `<uri>#/<N>` 跳页失效 → 37 张截图全同

- **现象**：渲染完成，收尾体检报 **37 张 PNG 体积都是 938.2 KB**（"太整齐"）
  → `md5sum png/*.png | sort -u | wc -l` 得 **1** —— **37 张内容完全相同**
- **根因**：`render-deck.py` 让 Chrome 跳到第 N 页的方式是给 URL 加 **`#/<N>` 哈希**，
  靠 deck 自带的 `runtime.js` 监听 `hashchange` 事件切页。
  而本册按母版规范是**「多张固定尺寸 `.slide` 纵向平铺」**结构，**没有 runtime.js**
  → 哈希被浏览器忽略 → **每次都截第一屏**
- **为什么容易漏**：退出码 0、37 个文件都在、体积也都像那么回事 ——
  唯一的破绽是「**体积完全一致**」，而这个破绽**只有在文件数 ≥3 且内容本该不同时**才显得可疑
- **解法**：写 `_中间文件/render-one.py` ——
  ① 从 index.html 解析出 37 个 `.slide` 块；
  ② 每页生成一个**独立临时 HTML**（只保留该页 `.slide` + 共享 CSS）；
  ③ 逐页 `--screenshot` 量体截图（`--window-size=1360,850`）
- **防复发**：**收尾必做 md5 唯一性核对**：`md5sum | sort -u | wc -l` 的**唯一内容数必须 == 页数**。
  **体积"太整齐"就是可疑信号**，先怀疑"截的是不是同一屏"

#### 坑 2 · 临时页子目录 → `<img src>` 静默 404（最阴险的一坑）

- **现象**：修好坑 1 后，截图里**页眉、页脚、章节标题、色块、细线全都正确**，
  **只有图片是碎图占位符**（浏览器画的"图片裂了"图标）
- **为什么最阴险**：**图片 404 时浏览器不抛错、不进 console 报错、不影响页面布局** ——
  它只是画一个占位符。**如果逐页肉眼翻 37 页，极易把它当成"这页设计就是这样"**
- **根因**：临时页落在 `01-工蜂产出/_pages/` **子目录**里，我生成临时页时
  只把 `<link href="assets/theme.css">` 改写成了 `../assets/theme.css`，
  **漏改了 `<img src="assets/xxx.webp">`** → 浏览器去 `_pages/assets/xxx.webp` 找 → 404
- **解法**：所有 `assets/` 引用（`<link>` **和** `<img>` **和** `srcset`）统一改写为**绝对 `file://` URI**：

  ```python
  assets_uri = (src.parent / "assets").resolve().as_uri()
  def absolutize(markup: str) -> str:
      return markup.replace('src="assets/',  f'src="{assets_uri}/') \
                   .replace("src='assets/", f"src='{assets_uri}/")
  ```

- **防复发（立为硬规矩）**：**不许靠肉眼看截图找碎图。**
  写 `_中间文件/verify-images.py` 探针 —— 用 Chrome `--dump-dom` 读**真实 DOM**，
  检查每张 `img` 的 `naturalWidth === 0` 即判失败。本册实测 **24/24 全部 > 0**。
  > 这与 2026-09-21「探针页放子目录 → theme.css 404」是**同一根因的两副面孔**：
  > 那次吃的是 CSS（页面骨架崩、几何全废但 dump-dom 照样成功），
  > 这次吃的是图片（只有碎图、其余全对）。**结论统一为：临时页/探针页的相对路径必须整体改写为绝对 URI。**

#### 坑 3 · 文件名骗人 + 我据文件名反向判定极性

- **现象**：把 `logo-白.png` 贴到深底满幅页/页脚徽章上，**标志完全不可见**
- **根因（两层）**：
  1. **文件名误导** —— 该文件实为「**透明底 + 墨色标志**」（文件名里的"白"指**白底场景**），
     而 `logo.png` 实为「**深绿底 + 米白标志**的成品展示图」（带底色，不是透明稿）。
     两个名字都往反方向暗示
  2. **我的判定被文件名带偏** —— 第一版 `make-logo-variants.py` 假定 `logo.png` 是透明墨稿，
     于是 classified 整体反向，得出「**墨 94.2%**」这个与事实相反的结论
- **诊断手段（这一步最关键）**：合成对照图 `_logo-candidates.png` ——
  `logo.png` / `logo-白.png` × {白底, 深底} = **4 格肉眼判读**，
  一眼确认 `logo-白.png` 才是透明底墨色标志、`logo.png` 是深绿底成品图
- **解法**：改以 `logo-白.png` 为**唯一来源**，用**双色互换**生成三件套 ——

  ```python
  is_red = r > 130 and g < 100 and b < 100
  if is_red:                                # 印章红保留
      primary/reverse = RED ; mono = INK
  else:                                     # 墨 → 按版本映射
      primary = INK ; reverse = CREAM(#F3E8D2) ; mono = INK
  ```

  产 `logo-primary.webp` / `logo-reverse.webp` / `logo-mono.webp`（均 785×719，裁掉透明边）
- **验证**：像素统计墨迹覆盖率 **9.5%**，与 BrandLock §2 记载的 **9.25%** 吻合（差 0.25pp = 抗锯齿边缘）；
  再合成 `_logo-variants-check.png` **二次肉眼核对**深底可用性
- **防复发**：
  1. **文件名不是事实。** 凡「标志 / 反白稿 / 透明稿」类素材，**必须白底 + 深底各合成一次肉眼核对**才能判极性
  2. **反白稿一律双色互换**（暗部→白、亮部→本版主色），**禁止把可见像素整体涂白** ——
     涂白会抹平内部结构，深色载体上只剩一个白剪影（这是 2026-09-18 碗香单的老坑，本次**再次踩到同一类**）
  3. 交付前把「源资产命名误导」写进遗留问题，建议主人正名

**沉淀**：
- 工具：`_中间文件/render-one.py`（逐页独立 HTML 截图 + md5 唯一性核对）、`verify-images.py`（DOM 图片探针）
- 判据：**① 唯一内容数 == 页数；② `naturalWidth` 全部 > 0；③ 反白稿必合成深底目视；④ 文件名不可信**
- **这三条已并入 `01-蜂王/验收清单.md` §G3「多张固定尺寸 deck」专项**（下次派工直接下发）
- 参考实现：`03-任务档案/20260921-土蚝小院品牌全案封装/`

### 2026-09-21 · 「原图直出 + 高清 PDF + 字距统一」三项改造（土蚝小院全案第二版）

**场景**：主人对已交付的 37 页品牌全案册追加三项要求 ——
① 门头与灯箱板块**不要景深效果、原图直出**；② logo 部分把 `logo-白` 资产替换「标志墨稿」；
③ **字体与英文统一优化，文字清晰、图片高清**。三项都不是"改个数值"，各踩了一个新坑。

#### 坑 1 · 去掉遮罩后页眉必压图（几何让位 > 遮罩）

- **做法**：满幅页原来用上下 `scrim` 渐变遮罩压住页眉页脚区。主人要求"不要景深效果"，
  我第一版直接 `inset:0` 让图片铺满整画布、删掉 scrim
- **现象**：P30 横版灯箱页**页眉与素材自带的书法字糊成一团** —— 「土蚝小院」字标压在
  素材的「人间…心归小院里」上；右上章节名与素材的「岭南小院 · 鲜味人间」重叠
- **根因（可算出来的）**：
  ```
  画布 1360×850（16:10），素材 1920×1080（16:9）
  contain 后：图高 = 1360 × 1080/1920 = 765px
  上下空带 = (850 − 765) / 2 = 42.5px
  而页眉带高 = 850 × 15% = 127.5px
  → 127.5 > 42.5，页眉必然落在图片上，且深进去 85px
  ```
- **解法**：**让图片为页眉页脚让位**，而不是给页眉页脚打遮罩 ——
  ```css
  .bleed-clean .stage{
    position:absolute; left:var(--mx); right:var(--mx);
    top:var(--hdr); bottom:9%;          /* 内容区内 */
    display:flex; align-items:center; justify-content:center;
  }
  .bleed-clean .bgimg{ width:100%; height:100%; object-fit:contain; }
  ```
- **⚠️ 实现细节**：不要用 `margin:auto + max-width` 那套（绝对定位元素上百分比/auto 尺寸
  解析不可靠 —— R7 老坑）。**用 flex 容器 + `object-fit:contain`**，一行搞定且确定性好
- **验证**：三页重渲染后目视 —— 页眉页脚落在纯深底上、图片完整无裁切、无任何模糊/渐变
- **判据**：**「图上叠字」的可读性问题，优先用「几何让位」解，而不是叠遮罩**。
  遮罩会把原图染色（主人正是因此要求去掉），几何让位不动原图一个像素

#### 坑 2 · `--force-device-scale-factor` 对 PDF 无效（对截图有效）

- **做法**：主人要"图片高清"，我第一反应是给 `--print-to-pdf` 加
  `--force-device-scale-factor=2`，期望 2× 光栅化提升清晰度
- **现象**：PDF 从 43.9 MB 暴涨到 **144.5 MB**，但**疑似没起作用**
- **验证方法**：写脚本对同一 HTML 分别用 scale=1 / scale=2 导出，比对
  ```
  scale=1   144.5 MB  pages=37  字体对象=389  图像对象=29
  scale=2   144.5 MB  pages=37  字体对象=389  图像对象=29
  ```
  → **完全一致**，说明 `--print-to-pdf` **忽略该参数**
- **真正的根因（意外收获）**：
  1. **文字一直是矢量**（字体对象 389 个）—— 所以"文字清晰"从来不是问题，**不需要 scale**
  2. 体积暴涨 100% 来自**我自己把素材长边从 1800 提到了 2720**（位图体积 ×4）
- **解法**：走折中档 —— 素材长边定 **1920**（PDF 73.8 MB），
  PNG 截图**保留 scale=2**（该参数对 `--screenshot` **确实有效**，可出 2720×1700 高清图）
- **防复发**：
  1. **别指望 scale 参数提 PDF 清晰度。** PDF 体积超限要动的是**素材分辨率**，不是打印倍率
  2. 区分两件事：`--screenshot` **认** `--force-device-scale-factor`；`--print-to-pdf` **不认**
  3. 验证参数是否生效，**用"改前改后字节同不同"来判**，别凭直觉

#### 坑 3 · 中文字距/行高散落硬编码 → 全册节奏不统一

- **现象**：全册有 **35 处**行内 `letter-spacing`，值有 `.05/.06/.08/.10/.12/.14/.16/.20/.22/.24/.28/.30em` 共 12 种，
  同一语义（如图注小字）在不同页字距不同；行高也有 `1.6/1.75/1.95/2.05/2.2/2.3` 混用
- **根因**：排版是逐页写的，每页顺手给一个"看着还行"的数值 —— **没有刻度就没有一致性**
- **解法**：
  1. CSS 建**字距四档**：`--ls-tight:.02em`（正文）/ `--ls-base:.06em`（小标题）/ `--ls-wide:.14em`（大标题）/ `--ls-en:.28em`（英文大写）
  2. CSS 建**行高四档**：`--lh-tight:1.28` / `--lh-mid:1.62` / `--lh-body:1.95` / `--lh-cap:1.72`
  3. **字体族统一**：`--font-en` 去掉 `Playfair Display`（与 Garamond 气质冲突且常不可用，
     回退不一致会让英文粗细忽粗忽细），改为 `EB Garamond → Georgia → Times New Roman` 单一主选链
  4. 写脚本把 35 处行内字面量按**视觉档位**（非机械按值）收编进变量，收尾正则复核**残留 == 0**
- **⚠️ 老式数字的全局解**：衬线体默认把 `01` 渲染成 `o1`。逐元素加 `lnum` 会漏，
  正解是**在 `body` 全局锁**：
  ```css
  body{
    font-variant-numeric:lining-nums;
    font-feature-settings:"lnum" 1;
  }
  ```
- **防复发**：**字距/行高必须建刻度，不许行内硬编码**；
  收尾用脚本把字面量收编，再正则扫一遍确认零残留（**只验"新值已加"不够，要验"旧值已清"**）

**沉淀**：
- 新工具：`_中间文件/prep-assets-hd.py`（素材高清重制 + 亮度实测）、
  `export-pdf.py`（高清 PDF + 页数核对）、`unify-tracking.py`（字距收编 + 双向复核）、
  `probe-pdf.py`（PDF 内嵌图像 dpi 探测）
- 判据：**① 图上叠字优先几何让位；② PDF 清晰度看素材分辨率不看 scale；③ 字距行高必建刻度**
- 参考实现：`03-任务档案/20260921-土蚝小院品牌全案封装/`

### 2026-09-27 · 「素材自带旧页眉带」的裁切判定：三个自动判据全废，正解是认结构不认底色（碗香 55 页封装）

**场景**：客户给的生产标注图**每张顶部都自带一条页眉带**（`品牌名 ｜ 栏目 —— 细横线 —— 编号胶囊`），
而册子要求「全册只呈现一处页眉」→ 必须把图内页眉带裁掉。共 32 张待裁。

**现象（三轮失败）**：

| 尝试 | 判据 | 结果 |
|---|---|---|
| ① 初始 | 「首个连续 ~13 行非白（>0.30）」= 内容起点 | **反向失效**：白底页眉图的小圆 logo + 稀疏文字达不到阈值，误裁 36–57px，**页眉整条留在册子里**（7 页双页眉） |
| ② 补救 | 「纯白间隔」分段 | **同样失效**：页眉与内容之间**没有稳定纯白分界**，返回值 8 或 None |
| ③ 再补救 | 目测缩略图定值（96–116） | **读数偏小**：1:1 复核图仍见残弧/残带；且另有两张反向**裁多**了（打包袋提手、文化墙顶部图标被切） |

**根因（两条，都指向「别用底色当判据」）**：

1. **背景不是纯白**：实测多张图的底是 `#F5F3EF / #F0EDE6` 一类**暖白**，
   纯白阈值（>0.30 判定非白）会把整片底判成「非白」→ 判据整体失准；
2. **页眉带与内容之间是「稀疏区」而不是「空白区」**：页眉下方的间隔里可能仍有极淡的
   装饰线/斜纹，没有 ≥6 行连续纯白 → 「纯白间隔」判据必然返回异常值。

**解法（确定性三件套）**：

1. **认「结构探针」而非底色**：这批判图里最靠下、最稳定的元素是**编号胶囊**（`A05`／`B06`…，
   实色填充、圆角矩形）。它在行剖面里表现为**一段「高覆盖 × 高暗度」的短块**，
   比「白底 + 细线」稳得多。做法：
   逐行统计 `rows_scan()` 的两个指标 ——
   - `cap_frac`：该行「非底色像素」占比（胶囊行 ≈ 0.25+）
   - `prof`：该行同时满足 `暗占比 ≥0.15` 且 `中占比 ≥0.08` 的行（栏目标题行）
   取**两者出现的最大 y** 作为页眉带底边 `bb`；再从 `bb` 往下**跳过抗锯齿残尾**（容忍 `>0.08` 若干行），
   落到「底色≥92%」的第一行作为 `cut`；若带后间隔 <6 行（贴内容）则取 `bb+4` 并标 `TIGHT`。
2. **底色自适应**：`bg` 不写死纯白 —— 采样图片四边中位色作为基准，容差按 **每通道 ≤6** 判「是否底色」，
   于是暖白底也能正确归类。
3. **裁后必出 1:1 边界复核图**（这条是硬要求）：按 `cut` 生成
   「y=cut−40 .. cut+120」的原尺寸切片并画红线标出裁切线，**逐张目视**确认
   ① 线上方无残字/残线/残弧 ② 线下方内容完整；**禁止用缩放缩略图目测定值或复核**（R9）。

**实测效果**：该判据对 32 张**全部命中**，与原手工推导逐张一致；最终实际改动了 **11 张**
（除报告指出的 7 张外，另含 `A06/C02/E03/F03` —— 后两张原本是**裁多**，一并纠正）。

**附带教训**：
- **裁切类返工最怕「单边思维」**：只盯「裁没裁净」会漏掉**「裁过头」**。
  收尾必须**双向抽检**（顶部看残留、内容看完整性），并**同时保住底部信息栏**（本例 32/32 规格栏完整）。
- 去重口径要写进任务书：本单任务书先写 33、后写 34，实测 **32**（`cut>0` 条目数）。
  **凡「N 张」这类口径，收尾用脚本数一遍并回写任务书**。

**防复发**：凡「素材自带页眉/页脚带需裁除」的任务 ——
**① 判据认结构元素（胶囊/实色块/装饰线）不认底色；② 底色自适应采样；③ 裁后 1:1 复核图逐张目视；
④ 双向抽检（残留 + 裁多）；⑤ 收尾脚本数口径并回写任务书。**

### 2026-09-27 · 改样式后的「零视觉 delta」证明：用像素回归代替肉眼过页（碗香 55 页封装）

**场景**：验收打回后要修三处规范项（行高刻度化 / 派生色注释 / 屏幕态取景），
它们**理论上不动视觉**，但「理论上」不足以放行 —— 55 页肉眼过一遍成本高且不可靠。

**解法（可复用）**：拿**同源的两套页图**做逐像素比对 ——
新集（视口==画布，满幅 1360×850） vs 旧集（1920×1080 整视口，按**画布矩形**裁到 1360×850）：

1. 画布矩形**由 CSS 常量推出、不靠检测**：`x0=(1920−1360)/2=280`、`y0=body padding-top=30`
   → 裁 `(280,30,1640,880)` 恰好 1360×850（先用行/列全分辨率游程扫一遍验证）；
2. 分段统计（页眉带 / 标题带 / 主体 / 页脚）而非只看全页均值 —— **差异落在哪一段，直接指向「谁改的」**；
3. 输出 1:1 对照图（左旧右新）做最终目视。

**本次结论**：17 页逐像素全同、27 页仅亚像素噪声（均差 ≤0.003）、11 页有实质差异但
**页眉带（y 0–128）差异 = 0.00 / 最大 0**，差异 100% 落在图区 ——
且这 11 页恰好等于**本轮被重裁过的 11 张素材**，即基线是「重裁前」的，
**差异是修复带来的正确变化，不是回归**。CSS 改动零视觉 delta 得证。

**防复发**：**凡「声称不影响视觉」的样式改动，一律用像素回归 + 分段定位出证**，
不靠肉眼、不靠推理。在此之前先确认基线是不是「同源」，否则会把「基线较旧」误判成「回归」。

**沉淀**：
- 脚本：`_work/regress_css.py`（像素回归 + 分段统计）、`_work/diff_where.py`（差异段定位 + 1:1 对照图）
- 参考实现：`03-任务档案/20260927-碗香PDF封装排版/`（含首轮 `02-验收单.md` 与复核 `03-验收单-复核.md`）

### 2026-09-27 · 「密排规范板」当页面整体贴 = 低级感的根因（碗香第二轮改造）

**场景**：首轮交付的 55 页全案册里，「标志标准组合与规范」是一整块生产标注板
（`board-标志标准组合与规范.png`，1672×941，板内 2 栏 × 上 2 段 / 下 4 段共 6 块内容）。
主人第二轮指令第一条就是「**将标志标准组合的拼图拆分为各自独立的组成部分，按一页或两页分别进行展示**」，
并同时要求「**整体排版与配色提升质感，高级、雅致、简约，避免廉价和俗气**」。

**根因（「低级感」的数学来源）**：

```
板宽 1672px，板内横向放 3 块 → 单块实际呈现 ≈ 500px
再按册子版心（1060.8px）缩放 → 单块 ≈ 300px 宽
而该块的原始语义是「安全留白 4 项 + 最小尺寸 3 档 + 使用说明 5 条」的规范细则
→ 300px 放不下细则，字号必然被压到读不出，观感即「密、挤、小」
```

**关键判断**：这**不是配色问题，是信息密度问题**。改颜色/换字体都救不了；
后来拆成 2 页独立展示后，单体呈现宽度从 ~300px 涨到 **~680px（2.3 倍）**，
再叠加「白底细边微投影」的画框承托，质感立刻成立 —— **高级感的来源是「留白 + 单体面积」，不是「色板」**。

**解法（判据 + 产线）**：

1. **判据**：素材若是「**一板多块**」形态（板内有多组互不相关的内容块），
   **板只作原件存档，入册一律拆分为单体图、一页一物**。
   与 `2026-09-22 一物料一页` 是同一价值取向 —— **篇幅不构成成本，单体呈现面积才是价值**。
2. **拆分粒度**：按「**块之间是否共享同一个语义标题**」定 ——
   同题多块（如「安全留白」的 4 项）合为一页；异题（构成说明 / 比例原则 / 安全留白 / 最小尺寸 / 反白单色 / 使用说明）**各自独立成页**。
   本单 6 块 → 按「一页 3 块 × 2 页」落地（主人拍板「拆 2 页」）。
3. **配色跟结构一起动**：拆分只是第一步；配套必须做 —— 页眉去通栏横线（改「轴线极简」）、
   新增细线页脚 + 页码、章节页改米白 + 细线、图版统一入 `.frame` 画框。
   **只拆不改承托 = 大图裸贴，观感反而更廉价**。
4. **结构三级化**：部分（Ⅰ 品牌基础 / Ⅱ 品牌文化 / Ⅲ 物料应用）→ 章节 → 物料；
   并把「品牌语言」并入「品牌文化」板块、整体**前移到品牌基础之后**（原排在物料段之后，属层级错位）。

**防复发**：
- **凡素材是「生产板 / 标注板 / 规范板」形态的，先问一句：它是一块内容，还是一板多块？**
  多块的就必须拆，且拆完必须重做承托（画框 + 留白），否则等于没改。
- **「拆图」类改造必须走 `deck-rework` 产线的「换素材 → 重算几何」铁律**，
  不能只换图片路径（本例标志页容器全部重写）。

### 2026-09-27 · 从密排板切图坐标连续 3 轮估偏 → 「切图四步收敛法」（碗香第二轮）

**场景**：把 `board-标志标准组合与规范.png`（1672×941）切成 6 张独立图。
看似只需给 6 组 `(x0,y0,x1,y1)`，实际**连错三轮**。

**三轮失败过程**：

| 尝试 | 做法 | 结果 |
|---|---|---|
| ① 目视缩略图估坐标 | 看着卡片边界填数 | 联系表显示**混入邻块**内容 |
| ② 按分区做窄带剖面 | 上栏按 y 分带、下栏按 x 分带 | ③ 号左缘**混入 ① 卡片**；② 号漏掉「贵州」印章 |
| ③ 按剖面修正 | 补窄 ② 左界、调 ⑤⑥⑦ 边界 | ② **左缘混入竖版标志**；⑤⑥⑦ **边界全错**；⑥ 号被切掉右半（只切到三个标签文字，三个 logo 稿样全丢） |

**根因（一条，但极难察觉）**：

> **板底色 `#F8F8F0` 与卡片底色 `#F7F1E6` 的色差低于任何合理阈值**
> → 一切「按底色找边界」的自动检测全部失效；
> → 而目视读缩略图**必然误判**（缩略图把 1px 边界压没了，R9 老坑）。

**解法：切图四步收敛法**（本单从此一次收敛，6 块全部对位）：

1. **点位采样定底色**（`probe_board_color.py`）——
   **不要猜底色**：在几个确定是"板"和确定是"卡片"的点位采样，把两个色值都打出来。
   实测得 板 `#F8F8F0` / 卡 `#F7F1E6` → **当场确认自动检测这条路走不通，改用结构性判据**。
2. **分区窄带剖面定模块带**（`detect_board2.py`）——
   按板的版面结构分两大区（`y<600` 左右两栏 / `y>600` 下方一栏），
   在每个区内取窄带逐列/逐行统计"非底色像素占比"，用**占比的突降点**定带边界。
3. **边缘洁净度自检**（最关键的一步）——
   对候选框算出后，**检查它的首列/末列、首行/末行**：
   ```
   edge_dirty = 该列/行「非背景像素占比」> 0.02   → 判脏，说明混入了邻块
   ```
   本轮靠它精确抓出两条：
   - `y=590` 附近是**满宽分隔线**（首行 T = 0.98~1.00）→ 那是板的分隔线，不是块边界；
   - ② 号左缘 `L = 0.53` → **混入了竖版标志**。
   **没有这一步，前两步的结论照样是错的。**
4. **在原板上画切框 + 标签后目视核验**（`_work/_cut-frames2.png`）——
   把最终 6 个框用色线画回原板，逐块看"框里是不是刚好一块、框外有没有漏内容"。
   **这一步的作用是给"数字结论"上最后一道人眼关**，而不是用来定坐标（定坐标靠步骤 1–3）。

**附带教训（⑥ 号被切掉右半）**：

- **对称性假设害人**：下栏前 4 块（③④⑤⑥）宽度相近，我按"等宽"推断 ⑥ 的右界，
  实际 ⑥ 含三个 logo 稿样、明显更宽，⑦ 从 x≈1370 才起。
- **破解手段**：切一张**诊断图** `_diag-567.png`（只裁 x880–1440 那一段的原尺寸图）单独看清 ⑤⑥⑦ 的真实结构。
  → **判据：当某一块的"宽度/位置"靠推断得出时，就把那一段单独裁原尺寸看，别在整板缩略图上推。**

**方法本身的边界（诚实登记）**：

- ⑥ 与 ⑦ 之间**没有纯空白带**（板内两块靠得极近）→ 切缝必然落在内容边缘上，
  这是**原板固有**，不判缺陷；已用步骤 4 目视确认视觉上无割裂感。
- 切出的 6 张图**自带板底 `#F7F1E6`**，与页面纸色 `#EDE2CF` 有轻微色差，
  在页面上形成"块边界"。**同属原板固有**，登记不处理（若要消除需重制板源）。

**防复发（立为硬规则）**：
**凡「从密排板 / 多块板切分模块」的任务 ——
① 先点位采样确认"底色能不能用来找边界"，不能就立刻转向结构判据；
② 用分区剖面定带，不用整板目视；
③ 候选框必过「边缘洁净度自检」（首末列/行非背景占比 > 0.02 判脏）；
④ 收尾必在原板上画框 + 标签目视核验；
⑤ 靠推断得出的边界，单独裁原尺寸诊断图看清楚再定。**

## 2026-09-27（第二轮）· ⚠️ **铁律复发**：`max-height:100%` 让 22 张图被静默裁掉

> **本条不是新坑，是既有铁律的第二次复发。**
> 铁律早在 **2026-09-18** 已立（见上方速查表）：
> 「固定画布下用百分比限高（`max-height:100%`）不可靠 —— 容器高度若由 flex/stretch 推导而来，
> Chrome 拒解该百分比、退回 auto → 图片按原始尺寸渲染，溢出容器被裁」，
> 并注明「已写进 VI 母版规范 §9；探针实测确认」。**本轮我主动把它换成了百分比，于是复发。**

### 现象

碗香第 4 轮全量渲染「成功 72/72、退出码 0、体积分布 30.5~1155.9 KB（差异显著）」，
**三项收尾指标全过**。但交付件里：

| 页型 | 素材原尺寸 | 实际呈现 | 被裁 |
|---|---|---|---|
| 板图页 ×5（P17/20/21/22/23） | 1672×941 | 容器只到 1152×478 | 左右各约 **260px**，板图左栏文字与右栏「使用说明」整块丢失 |
| 门帘 P32 | 1086×1003 | 1086×543 | 上下各约 **230px** |
| 服务员服装 P37 / 厨师服装 P38 | 1024×1536 | 1024×543 | 上下各约 **495px** |
| 营业时间牌 P39 / 品牌故事 P64 | 1024×1064 | 1024×543 | 上下各约 **261px** |
| IP文化展示 P66 / F05 主题视觉 P67 | 1086×1003 / 1049×1039 | 同上 | 上下各约 **230/248px** |
| **主题海报 ×4（P68–P71）** | 1024×1536 | 1024×543 | **上下各约 495px —— 海报顶部标题带与底部 logo 带全部丢失** |
| 名片 P28 / 饮料杯 P54 | 1619×971 / 1448×752 | 高 689.7 / 597.2 裁到 543 | 上下各约 73px / 27px |

合计 **22 张图**（5 板图 + 17 物料/海报）受影响。

### 根因

第 4 轮把上一轮（r3，已交付版）里**正确的 px 硬编码上限**
```css
.plate .shot img{ max-width:1054px; max-height:676px; width:auto; height:auto; }   /* r3 · 正确 */
```
"改良"成了包一层 `.frame` + 百分比：
```css
.frame{ display:flex; align-items:center; justify-content:center; overflow:hidden; }
.plate .shot>.frame{ max-width:100%; max-height:100%; }
.plate .shot img{  max-width:100%;  max-height:100%;  width:auto; height:auto; }      /* r4 · 坏 */
```

失效链条：

1. `.shot` 的高度来自 `flex:1`（用在这**不是** `height` 属性；`.shot` 的 computed `height` 仍是 `auto`）；
2. `.frame` 是 `.shot` 的 flex item，靠 `align-items:stretch` 拿到 used height（545.4px）；
3. 但 **CSS 百分比 `max-height` 的基准是包含块的 `height` 属性，不是 used value** ——
   `.frame` 的 `height` 属性是 `auto` → `img { max-height:100% }` 解析为 **`none`**；
4. 于是 `img` 退回原尺寸 → 超出 `.frame` → 被 `.frame{overflow:hidden}` 裁掉。
   （`max-width:100%` 能生效，是因为宽度方向的百分比不依赖内容高度 —— 所以**横幅图看着是好的，
   只有竖版图出事**，这进一步掩盖了问题。）

### 为什么没被拦住（真正的教训）

本条的价值不在"又碰到一次"，而在**收尾验收的缺口**：

- 收尾验的是「① 张数 ② 体积分布 ③ 退出码 / PDF 页数 & MediaBox」——
  这三项**在图片被裁的情况下全部正常**（甚至体积分布还很"健康"，因为裁切后的图内容不同）；
- 肉眼看**联系表缩略图**也发现不了：竖版图被裁中间 35% 后，缩略图上就是"一张横图"，看不出异常；
- **唯一能拦住它的是几何量测**：`img` 渲染尺寸 vs 容器尺寸。

> **判据：图版类交付的收尾必须增加第 4 项 —— 「图版贴合体检」。**
> 前三项过 ≠ 内容对；**"内容是否完整"必须单独量**。

### 解法（本轮落地）

回到 px 上限（铁律原文），并用 `fit-content` 让图版贴合图片、不再出现"大白条"：

```css
/* R7：固定画布下尺寸硬编码 px —— 百分比上限在「包含块 height:auto」时解析为 none，会致原尺寸溢出被裁 */
.bd>.frame{ width:fit-content; height:auto; }
.bd>.frame>img{ display:block; width:auto; height:auto; max-width:1150px; max-height:594px; }
.plate .shot>.frame{ width:fit-content; height:auto; }
.plate .shot>.frame>img{ display:block; width:auto; height:auto; max-width:1150px; max-height:540px; }
/* 海报页另立页型：左图右栏，竖版满高 */
.slide.poster .bd{ display:flex; gap:0; align-items:center; }
.slide.poster .frame>img{ display:block; width:auto; height:auto; max-width:1000px; max-height:700px; }
```

副产品（都是收益）：
- 板图页原来把 705px 内容区里的图台写死 `height:478px`，**白白浪费 120px**；
  改后板图由 845px 宽涨到 **1055px 宽**（+25%），规范板小字可读性显著改善；
- 图版由"满宽白条"改为**贴合图片的白卡**，竖版图变成居中卡片，留白干净（原本满宽白条 + 小图是"廉价感"的直接来源）；
- 4 张主题海报从"被裁到只剩中间一条"改为**左图右栏**：海报满高 467×700，右栏承载 承载文案 / 文案角色。

### 机检出口（本轮补上，这才是防复发的关键）

新增工具：`04-知识沉淀/工具/deck-benchmark/probe_fit.py`

```
python probe_fit.py <index.html> [slide选择器=.slide] [chrome.exe]
```

`CROP`（图 > 容器 → 被裁）/ `DISTORT`（渲染比例 ≠ natural 比例）/ `COLLAPSE`（容器高塌陷），
收尾打印唯一结论 `PASS` / `FAIL(n)`。

**已做双向验证**（工具本身也要过"能抓到已知坏样本"这一关，否则是假通行证）：

### 防复发（硬规则）

1. **任何"改良 CSS"只要涉及尺寸约束，先问：新写法是不是百分比？基准元素有没有确定的 `height`？**

   属于**未立项的重构**；凡要替换已有正确实现，须在任务图里显式列一条并配等价的机检。

## 2026-09-27（第三轮）· 目录页 **219% 溢出**：10 个章节块只显示 4 个，全程无告警

**目录页写了 10 个章节块，页面上只显示前 4 个**（第 4 个「品牌入口」还被裁掉下半），


10 个块排 5 行；每块高 = padding 48 + 章节名 ≈40 + 条目 n×22。
「品牌基础」12 条、其余块 3~9 条 → 5 行合计 **1545px**，远超内容区 705px。

上一次是**图片**按原尺寸溢出容器被裁；这一次是**文本栅格**溢出容器被裁。
**同一个机制**（`overflow:hidden` + 内容超容器），只是载体从图片换成了文字块。
**「收尾指标全过」再次没能拦住它** —— 溢出内容根本不进入产物，产物"看起来"完整。

> **判据：内容完整性必须单独量。张数 / 体积 / md5 / PDF 页数，四项都不是它的判据。**

① 目录重排：五批物料**合并为一个「品牌物料」格**（只列批次名 + 起始页码），块数 10 → 6、两列 3 行；
② 收紧 `.toc-blk`（padding 24→12、章节名 23→20px、条目 12→11px、行 padding 4→2）；
③ 目录头收紧（38→34px）。
结果 **1545px → 641px（91%）**，六块完整落在一页内。

递归量每页容器内**所有元素**的最大 bottom vs 容器 bottom，逐页报 `OVERFLOW` / `(偏空)`，

4. 内容不足（fill < 60%）不算缺陷但影响观感 —— 理论页可用

## 2026-09-27（第四轮）· 判据补充：「两页体积显示相同」不等于渲染失败

### 现象

碗香第 6 轮（删 P15/P16）抽页复核时，`render-deck.py` 输出：

```
  [ 3] OK        57.7 KB
  [61] OK        57.7 KB
```

两页体积显示**完全相同** —— 而第 4 轮刚踩过「72 张截图体积全同（86.7 KB）、根因是漏了导航脚本」，
**第一反应就是复发**。

### 实测澄清

```bash
md5sum png/slide-3.png png/slide-61.png
# 2de30fb3272b90d3623c62e4f0f5bcb3  slide-3.png
# 6a929c8330be41e420f210ae96bf0a1c  slide-61.png
ls -la:  59057 B  vs  59043 B     # 差 14 字节
```

内容完全不同（P3 目录页 / P61 深底尾页），**md5 不同、字节不同**。
`57.7 KB` 是**四舍五入到 0.1KB 的显示精度**造成的巧合。

### 判据（明确下来）

| 判据 | 能否用 |
|---|---|
| 体积**显示值**是否互不相同 | ❌ **不能** —— 精度仅 0.1KB，浅底少字页（扉页/尾页/章节页）集中在同一档很正常 |
| **`md5` 唯一数 == 页数** | ✅ **唯一可靠判据** |
| 体积是否在合理量级（非 0 / 非异常小） | ✅ 辅助，用于发现「零产出」（与「小体积 PNG ≠ 空白页」互补） |

> **收尾时只认 `md5 | sort -u | wc -l == 页数`。**
> 体积显示相同 → **先核 md5 再下结论**，不要直接判定渲染失败并重跑（白烧一轮 2 分钟渲染）。

**关联**：本轮同时确认 `probe_fit.py` + `probe_overflow.py` 均 PASS，即四个内容完整性闸门
（md5 唯一数 / 贴合 / 溢出 / 交付件本体）全过。

## 2026-09-28 · 判据补充：换图后必核「新图比例 vs 页面规格栏声明比例」

### 现象

碗香第 7 轮（主人令：P13 换图 / P15 删页 / P52–56 换五张正文图）按最小改动**只替换图片文件**，
页面的四格规格栏（建议尺寸 / 材质 / 工艺 / 应用位置）**沿用原物料数据不动**。

换完图后量「新图宽高比」vs「规格栏『建议尺寸』的宽高比」：

| 页 | 物料 | 规格栏声明 | 声明比例 | 新图比例 | 偏差 |
|---|---|---|---|---|---|
| P51 | 主Slogan平面展示 | 1200 × 600 mm | 2.000 | 2.634 | **32%** |
| P52 | 品牌故事 | 900 × 1200 mm | 0.750 | 0.718 | 4% ✅ |
| P53 | 品牌文化墙 | 3000 × 1600 mm | 1.875 | 2.631 | **40%** |
| P54 | IP文化展示 | 900 × 1200 mm | 0.750 | 0.819 | 9% |
| P55 | 小炒剔骨鸡主题视觉 | 700 × 1000 mm | 0.700 | 0.694 | 1% ✅ |

**关键**：旧图比例**同样不符**（旧 F01 = 2.889、旧 F03 = 2.704）
→ 这**不是本轮引入的缺陷**，而是「正文图 ≠ 生产尺寸裁切稿」这一既有状态。

### 为什么仍要单独量

**「只换图」是改造里最容易被当成"零风险"的动作，但它会静默地把页面推入「图文不符」状态**：

- **五步收尾全部过**：张数 / md5 唯一数 / 尺寸集合 / 时间戳 / 贴合 / 溢出 —— 六项都不看「图与规格栏说的是不是同一件事」；
- **联系表也看不出**：缩略图里规格栏的文字小到不可读；
- 唯一能发现的是**把两边的数字拿出来做除法**。

### 判据（明确下来）

```python
# 素材替换后，逐条比对
r_img = new_image.width / new_image.height          # 新图实际比例
r_spec = 声明宽 / 声明高                              # 规格栏「建议尺寸」比例
# 偏差 > 6% → 标记「图文不符」，上报主人，不擅自改数据
```

**处置原则**（不得擅自改规格数据 —— 那是「样张零编造」的反向违规）：

1. **如实上报**：列出偏差表 + 说明「旧图是否同样不符」（区分**本轮引入**还是**既有状态**）；
2. 给主人三个选项：① 保持（现状）② 提供新图对应实际尺寸后更新 ③ 规格栏改「—」；
3. **绝不自行编造**一个新尺寸去"对上"图片比例 —— 两种做法都是错的（编造数据 / 擅改有源数据）。

### 顺带记下的机制说明

`plate`（物料页）页型的结构是「顶部标题层 → 居中贴合图版 → 底部四格规格栏」，
**规格栏数据是第 4 轮从生产标注图逐字提取的**（图像上的标注被裁掉，信息搬到页面上）。
因此**换图 = 换画面，规格栏不动**在语义上是对的 —— 但前提是新旧图对应同一物料。
本轮新图是「正文」版（去标注的成品画面），**大概率对应同一物料，只是版式外形不同**，故判定为可接受。

**关联工具**：五步收尾（`probe_fit.py` / `probe_overflow.py`）**不覆盖本判据** ——
它属于**内容语义一致性**检查，与几何完整性检查是两件事。

## [2026-10-06] 否决后增量修补 = 越改越脏（跨项目印证）

**来源**：分析 `amirmushichge/brand-system-skill`（AI 品牌系统工作流协议）时发现其「规则 19」，

**现象**：一个方向/实现被否决后，仍在其上做局部修改 → 产出一团脏东西。

**根因（一句话）**：**在"已经不干净"的基础上叠加新决策** —— 污染源没有被物理隔离。

**本库既有同根案例**：
- 2026-09-27：把已验证正确的 **px 上限"改良"成百分比** → 22 张图被裁（还犯了第二次）
- 批量替换脚本**吃掉 `.art-box` 包裹层** → 图片裸挂、尺寸规则整条失效

**外部验证**：`brand-system-skill` 把它写成了硬禁令 —— *"Never blend a rejected direction with a
replacement direction."* 并列明混用后果：**混合字体、残留材质、矛盾颜色、视觉伪影**。

**解法（四条，已写进制度总纲 §七）**：
1. **量化判据**：反馈触及基础系统 **≥2 项 → 判定「推倒重建」**，不是"调整"
   （基础系统 = 整体调性 / 字体系统 / 主色逻辑 / 材质语言 / 包装架构 / 视觉层级 / 摄影方向 / 客群适配 / 感知价格档次）
2. 旧稿标记 `REJECTED — 不得再作视觉参考`
3. **只保留抽象决策**（KEEP 列表），其余全部丢弃
4. ⛔ **绝不把被否决的稿子当生成参考附上**；从零构建

**防复发**：① 判据可计数，不靠感觉　② 「否决稿隔离」设为独立动作　③ 验收单增 `PRESERVE` 字段
（修正时明确"什么不许动"）—— 否则"修 A 坏 B"无从追责。

## [2026-10-10] 页面级 class 与组件级 class 撞车 —— 一个根因、两个症状

**来源**：`20261010-高性价比人生指南蒸馏封册`（A4 竖版 43 页蒸馏册）。

### 症状（两个，看着毫不相干）

| # | 症状 | 表面像什么 |
|---|---|---|
| ① | `PDF 页数 44 ≠ slide 数 43`，**P04 整页空白** | 「@page 尺寸差 1px」「content 溢出画布」（R8 老坑） |
| ② | 43 张截图**全长一个样**（都是目录页） | 「headless 没套用 `@media screen` 可见性」 |

### 根因（同一个）

页面容器由页面类型派生 class 名：

```html
<section class="slide toc-p">          <!-- 目录页 -->
```

而主题 CSS 里**早已有一个 `toc-p`，是给「目录行」用的**：

```css
.toc-p{ display:flex; align-items:baseline; gap:10px;
        padding:8px 0 7px; border-bottom:1.5px solid var(--ink); margin-top:22px; }
```

于是**目录页这个 `<section>` 被目录行的样式命中**，实测计算值：

```
section.slide.toc-p  →  margin-top:22px ; padding:8px 0px 7px ; border-bottom:1px ; display:block(print)
参照：section.slide.pg-cover / .pg-ent  →  margin/padding/border 全 0
```

两个症状由此分叉：

- **打印媒体**：`margin-top:22px` 把整页在分片流里**下推 22px** →
  页面高度 1123px 从「页顶对齐」变成「跨页」，尾部 22px 落到下一页 →
  `page-break-after:always` 再补一次分页 → **多出一整页**（该页只剩 22px 目录尾巴）。
- **屏幕媒体**：`.toc-p{display:flex}` 与 `@media screen{.slide{display:none}}`
  **特异性相同（都是单个 class）** → **后出现的 `.toc-p` 胜出** →
  目录页 `display` 计算值 = `flex` → **任何一页下它都可见**。
  目录页高 1123px 正好占满视口 → **每张截图顶部拍到的都是它**。

### 定位过程（可复用的三招）

1. **幽灵页溯源**：给前 8 页注入互不相同的底色 → 导出 PDF → 逐页扫像素。
   立刻读出「目录页（蓝）在 P3 从 y=22px 才开始，尾巴落在 P4 前 22px」。
2. **复制/移除/重排实验**（不是改样式）：`dup-toc` → 空白页从 1 个变 2 个；
   `no-toc` → 空白页消失；**`toc-moved-to-end` → 消失**（后面没有页就不裂）。
   → 锁定「目录页 + 它后面还有内容」这个组合。
3. **CDP 探针量 print 媒体真值**（`Emulation.setEmulatedMedia({media:'print'})` + `Runtime.evaluate`）：
   各页 `top` = `0 / 1123 / 2268 / 3391 …` —— **第三张应为 2246 却是 2268，正好多 22px**，
   且 `body.scrollHeight` 恰比 `43 × 1123` 多 22。
   再读计算样式 → `margin-top:22px` 直指 `.toc-p`。

> ⚠️ 中途 12 个「改样式」候选（页高 1118/1122、`@page` 改 1130、`break-inside:avoid`、
> 删页眉/页脚/空白文本节点、`body{overflow:hidden}`…）**全部无效**，
> 因为病根不在样式值，而在**哪条规则命中了哪个元素**。
> **样式全改不动的 bug，要查「选择器命中关系」，不是查「属性值」。**

### 解法

1. **页面级 class 独立命名空间**：`pg-cover / pg-preface / pg-toc / pg-part / pg-ent / pg-end`。
   组件级保留语义名（`.toc-p` 仍是目录行）。
2. **print 块几何硬化**（兜底，防止再被任何工具类挤动）：

```css
@media print{
  .slide{ display:block !important; margin:0 !important; padding:0 !important;
          border:0 !important; overflow:hidden !important;
          page-break-after:always; break-after:page; }
}
```

### 防复发

- **立铁律**：deck 的「页面容器 class」必须带独立前缀（`pg-`），**不得与组件/行级 class 同名**。
  命名前先 `grep "\.<候选名>" theme.css` 确认零命中。
- **收尾加一项**：导出 PDF 后除「页数 == slide 数」外，**再核 `body` 分片流里各 `.slide` 的 `top`
  是否为 `n × 画布高`**（连续递增、无跳变）—— 这是「页面几何被污染」的唯一机检出口，比页数更早发现。
- **教训**：**绕开 ≠ 修好**。用内联 `style.display` 绕过后屏幕端看似正常，
  但病根留在打印端，几小时后以另一个面貌复发。
  **任何「改了就好、但说不清为什么」的补丁，必须继续追根因。**

## [2026-10-10] 「一对多」归属的登记表：键必须带归属维度

**场景**：A4 蒸馏册生成目录页码（两遍法：先分页、再回填页码）。

**现象**：目录 40 行，**11 行页码错误**。例：贰 金钱篇下的「反面清单」标 **7**，
而 7 是 壹 健康与寿命篇的页码（贰 篇从 20 页才开始）。

**根因**：原著的一个「节」可以同时向两篇供稿 —— 例如「反面清单」里的条目，
一部分换回**健康与寿命**、一部分换回**金钱**。重排版式后，同一个节标题在
两篇的页面上各出现一次。而登记表写成：

```python
sec_page = {}                                    # 键 = 节号
...
if b["kind"] == "sec" and b["sec"] not in sec_page:
    sec_page[b["sec"]] = pno                     # 只记第一次出现
```

→ 第二篇的目录行取到的是**第一篇的页码**。

**解法**：键带上归属维度。

```python
sec_page.setdefault((p["pian"], b["sec"]), pno)  # 键 = (篇, 节号)
```

复验：**40/40 行页码与实际页位逐一吻合**。

**防复发**：
- 凡「同一实体在多个上位分组里各出现一次」的登记/映射，**键必须含分组维度**；
  单键登记 + `setdefault` 是这一类的典型陷阱。
- **目录/索引类交付必做「逐行回验」**：不能只验「生成了 N 行」，
  要把每行标注值与**实际页位**比对，输出 `错行数 / 总行数`。
  （本册判据：`目录标 == 该篇下该节实际出现的页`）

## [2026-10-10] 改版式后忘了重测「实测卡高」—— 分页预算与内容对不上

**场景**：A4 蒸馏册改「分条」版式（条目卡重排：条号悬挂、徽章上提、删掉 chips 行）。

**症状（若不做这一步就会踩）**：分页预算用**旧版卡高**、页面装的是**新版卡片** →
每页实际内容都比预算高 → 全册静默溢出，`overflow:hidden` 把尾部裁掉，前四步机检全过。

**根因**：`card_heights.json` 是「浏览器实测卡高」的快照，被 `build_body()` 当作**唯一分页依据**。
它是**结构派生的产物**，不是常量 —— 只要动了影响卡高的任何 CSS（字号 / 行高 / 内边距 / 增删元素），
快照立即作废。

**解法 / 流程固化**：

```bash
python _work/build_book.py --measure   # 用新 CSS 渲染全部卡片 → _measure.html
python _work/run_measure.py            # Chrome 量真实高 → card_heights.json
python _work/build_book.py             # 再重建（此时分页才用上新高度）
```

已写进派工单**显式勾选项**：「**卡高重新实测**（旧值作废）」，并升级为制度 **R15**。

**一般化**：凡「**派生自结构、又被当作后续输入**」的中间产物（实测尺寸、目录页码、索引表、
字数统计…），都要在源头结构变更后**标记作废并重算**；不要指望它自己更新。

## [2026-10-10] 删页 / 改名后，页码基准与署名落点双双错位

**场景**：同一册，按要求删掉「序」（原 P2）与「来源与许可」（原 P43），并把书名整册换掉。

**症状**：① 页脚编号从 **3** 起跳（应为 2），全册页码整体错 1；② 尾页删掉后，**CC BY 署名几乎无处落**。

**根因**：
① 页码是**三处互锁**的：`pno` 基准、`TOTAL`、以及**目录页自己的 `page_no`**。
改前两处、漏改第三处 → 页脚起点错位。（`pno` 与 `TOTAL` 好改，目录页因为「它自己就是第 2 页」最容易被漏）
② 尾页往往就是**署名页**。删它是内容决定，但 CC BY 的「作者 + 作品名 + 来源 + 许可」四件套
必须有别的落点；同时**改名不能把原著书名一起抹掉**（作品名是署名的一部分）。

**解法**：
- 页码：改基准后**跑机检**「页脚序列 == `2..N` 连续」+「目录逐行回验」，别靠眼看。
- 署名：把四件套**显式迁移**到封面脚注 + **每页页脚**（页脚天然是「页页都有」的署名位），
  并把「原著书名」保留在署名串里。验收时数一遍：`署名串出现次数 == 有页脚的页数 + 封面`。

**防复发**：升级为制度 **R16**（删页/改名/调序 ⇒ 页码基准与署名落点同步重算并回验）。
